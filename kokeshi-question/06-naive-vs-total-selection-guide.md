# kokeshi-question #06: naive と total の使い分け — トラフィックの性質から選ぶための資料

関連: [#05 バーンレートの計算と評価](05-burn-rate-step-by-step.md) / [#01 リクエスト数に差がある時間帯の SLO](01-slo-error-budget-low-traffic.md)

---

## 0. 結論（1枚で）

- **naive** は「**システムが壊れているか**」（エラー率）を測る。**total** は「**ユーザー被害で予算がどれだけ速く減っているか**」を測る
- 2つは `total = naive × r` でつながっている（r = その窓のリクエスト数 ÷ 平均）
- **r ≈ 1 なら同じ値**。差が出るのは r が 1 から離れたときだけ
  - **r が小さい（谷）**: naive は誤報しやすい / total は全停止を見逃しうる
  - **r が大きい（山）**: naive は被害を過小評価する / total は壊れていなくても鳴りうる
- なので「どちらか1つ」ではなく、**トラフィックの性質（r の分布）を測った上で、目的別に組み合わせる**

> この資料の境目の数値（「N が 69件未満」など）は式から導いたもの。タイプ分けの目安や組み合わせ条件（§6〜§7）は、
> Google / Hartmann の資料にある形ではなく、それらを組み合わせた**この資料の提案**。

## 1. 定義

| 記号 | 意味 | 例（この資料の前提） |
|---|---|---|
| SLO | 成功率の目標 | 99.9% |
| 1 − SLO | 許容エラー率 | 0.1% |
| 周期 | SLO を評価する期間（**直近**の期間。カレンダーの先月ではない） | 30日（= 720時間） |
| N | その窓に実際に来たリクエスト数 | — |
| N̄ | 窓内の平均リクエスト数 = 直近30日の1時間あたり平均 × 窓の長さ | 1時間窓なら 10,000件 |
| f | その窓の失敗数 | — |
| e | その窓のエラー率 = f ÷ N | — |
| r | トラフィック比 = N ÷ N̄ | 夜 0.01、セール 20 など |
| T | 人を呼ぶバーンレートの基準 | 14.4（1時間窓、Google 標準） |
| 予算 | 周期内に失敗してよい件数 = (1 − SLO) × 周期の総リクエスト数 | 7,200件 |

```
naive = (f ÷ N)  ÷ (1 − SLO) = e ÷ (1 − SLO)
total = (f ÷ N̄) ÷ (1 − SLO) = naive × r
```

周期は SLO に合わせる。Google の基準（14.4倍など）は 30日周期の値。2023年ノートブックは 28日周期（基準は 13.44倍）。

## 2. それぞれ何がわかるか

| | naive | total |
|---|---|---|
| 推定しているもの | エラー率 e（1リクエストが失敗する確率） | 予算の消費スピード（失敗**件数**のペース） |
| 答えている問い | **システムは壊れているか？** | **ユーザー被害で予算が危ないか？** |
| トラフィックの影響 | 受けない（e が同じなら値も同じ） | 比例する（同じ e でも r 倍） |
| 値の意味 | 許容エラー率の何倍のエラー率か | 1倍のペース（1時間 10件）の何倍の失敗件数か |
| 予算との一貫性 | 弱い（予算は件数なのに率で見る） | 強い（予算と同じ「件数」で見る） |
| 実装 | 監視ツールの標準（Google Workbook の形） | 分母の N̄ を別途用意する（Hartmann: 周期の総数を定数にして1日1回 cron で更新） |

## 3. 誤検知と見逃しが起こる境目（式から）

### 3-1. naive の誤報（谷で起こる）

1件の失敗だけで naive が基準 T を超える条件:

```
1 ÷ N ÷ (1 − SLO) ≥ T   ⇔   N < 1 ÷ (T × (1 − SLO))
SLO 99.9%, T = 14.4 のとき:  N < 1 ÷ (14.4 × 0.001) ≈ 69件
```

**システムが SLO 通り（e = 0.1%）で何も壊れていないのに**鳴る確率:

| 1時間の N | 鳴るのに必要な失敗数 | 1時間で誤報する確率 | 夜8時間で1回以上誤報する確率 |
|---|---|---|---|
| 10 | 1件 | 1.0% | 7.7% |
| 20 | 1件 | 2.0% | 14.8% |
| 50 | 1件 | 4.9% | **33%** |
| 69 | 1件 | 6.7% | **42%** |
| 100 | 2件 | 0.46% | 3.7% |

→ 夜に1時間50件程度のサービスなら、**3晩に1回は誤報で起こされる**。

### 3-2. total の見逃し（谷で起こる）

エラー率 e の障害で total が T に届かない条件:

```
r × e ÷ (1 − SLO) < T   ⇔   r < T × (1 − SLO) ÷ e
全停止（e = 100%）なら:   r < T × (1 − SLO)
```

| SLO | 全停止を total が見逃す r | 意味 |
|---|---|---|
| 99.9% | r < 0.0144 | 平均の 1.4% 未満しか来ない時間帯 |
| 99% | r < 0.144 | 平均の 14% 未満 |
| 98%（2023年ノートブック） | r < 0.288 | 平均の 29% 未満 |

→ **SLO が緩いほど、total は全停止を見逃しやすい**。

### 3-3. total の「対応のしようがない」アラート（山で起こる）

システムが普段通り（エラー率 e₀）でも total が T を超える条件:

```
r × e₀ ÷ (1 − SLO) ≥ T   ⇔   r ≥ T × (1 − SLO) ÷ e₀
e₀ が SLO ちょうど（0.1%）なら:  r ≥ 14.4
e₀ が SLO の半分（0.05%）なら:  r ≥ 28.8
```

→ トラフィックが平均の十数倍以上に跳ねるサービスでは、**壊れていないのに鳴る**。
（予算は本当に減っているので、予算の観点では正しい。ただし直すものがない）

### 3-4. naive の見逃し（山で起こる）

予算は基準以上の速さで減っているのに、naive が T に届かない条件:

```
naive < T  かつ  total = naive × r ≥ T   ⇔   T ÷ r ≤ naive < T
```

→ r = 3 なら、naive が 4.8倍〜14.4倍の間の障害は、**被害は大きいのに naive では鳴らない**。

## 4. 具体例で比較

前提: SLO 99.9%、周期30日、平均 1時間 10,000件、予算 7,200件、基準 14.4倍（1時間窓）

| # | 状況 | N | f | r | e | naive | total | 使った予算 | システム異常？ | naive の判定 | total の判定 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| S1 | 普段の昼 | 10,000 | 5 | 1 | 0.05% | 0.5 | 0.5 | 0.07% | なし | ✓ 鳴らない | ✓ 鳴らない |
| S2 | 夜、偶然の2件 | 100 | 2 | 0.01 | 2% | **20** | 0.2 | 0.03% | なし | ✗ **誤報** | ✓ 鳴らない |
| S3 | 夜、**全停止** | 100 | 100 | 0.01 | 100% | 1,000 | **10** | 1.39% | **あり** | ✓ 鳴る | ✗ **見逃し** |
| S4 | 夜、半分失敗 | 500 | 250 | 0.05 | 50% | 500 | 25 | 3.47% | あり | ✓ 鳴る | ✓ 鳴る |
| S5 | セール、普段通り | 200,000 | 200 | 20 | 0.1% | 1 | **20** | 2.78% | なし | ✓ 鳴らない | △ **鳴る（直すものがない）** |
| S6 | 混雑中に軽い劣化 | 30,000 | 150 | 3 | 0.5% | **5** | 15 | 2.08% | あり | ✗ **見逃し** | ✓ 鳴る |
| S7 | 昼に劣化 | 10,000 | 200 | 1 | 2% | 20 | 20 | 2.78% | あり | ✓ 鳴る | ✓ 鳴る |

読み方:
- **r = 1（S1, S7）**: 2つは同じ判定
- **r が小さい（S2〜S4）**: naive は誤報（S2）、total は全停止の見逃し（S3）
- **r が大きい（S5, S6）**: total は直すもののないアラート（S5）、naive は被害の見逃し（S6）

## 5. メリット・デメリット

| | naive | total |
|---|---|---|
| **メリット** | ・監視ツールの標準機能で書ける<br>・「壊れているか」が直接わかる<br>・谷の全停止を確実に拾う（S3）<br>・トラフィックの急増だけでは鳴らない（S5） | ・夜の少数の失敗で鳴らない（S2）＝チーム健全性<br>・予算の減り方と一致し、ユーザー被害に比例<br>・混雑時の中程度の劣化を拾う（S6）<br>・昼夜で同じ基準が使える |
| **デメリット** | ・谷で誤報が多い（N < 69件で1件の失敗で鳴る）<br>・混雑時の被害を過小評価（S6）<br>・予算（件数）と単位が合わない | ・谷の全停止を見逃す（S3、SLO が緩いほど顕著）<br>・急増だけで鳴ることがある（S5）<br>・分母 N̄ を別途用意する手間<br>・**常に少量のサービスでは効果がない**（r ≈ 1 なので naive と同じ） |
| 向いている目的 | システムの異常検知 | 予算の保護、ユーザー被害の検知 |

## 6. トラフィックのタイプ別の適用基準

### 6-1. 3つの軸

| 軸 | 測るもの | 効いてくるもの |
|---|---|---|
| A. 量 | 窓あたりの N の最小値 | §3-1 の誤報（N < 1 ÷ (T × (1 − SLO))） |
| B. 予測できる変動 | 昼夜・曜日の周期的な波の深さ（r の下側） | §3-1 の誤報、§3-2 の見逃し |
| C. 予測できない変動 | 周期パターンを除いた後のばらつき（r の上側の裾） | §3-3 の直すもののないアラート、§3-4 の見逃し |

### 6-2. 4つのタイプ

| タイプ | 判定の目安 | 例 | 主に使う方式 | 併用するもの |
|---|---|---|---|---|
| **① 安定・大量** | 最小 N ≫ 69、r が 0.5〜2 程度に収まる、D が小さい | 常時動く基幹 API | **naive**（total とほぼ同じなので標準で十分） | 全停止検知 |
| **② 安定・少量** | 平均 N でも 69 前後以下、r ≈ 1 | 管理画面、社内ツール | **どちらでも効果は同じ（total でも解決しない）** | Google の低トラフィック対策（合成トラフィック、サービスを束ねる、窓を長くする、SLO を見直す） |
| **③ 周期的な波が大きい** | r の 1% 点が小さい（例: < 0.2）、周期パターン除去後の D が大きく下がる | 一般向け EC、メディア | **total** | 全停止検知（§3-2 の見逃し対策） |
| **④ スパイクしやすい** | r の 99% 点が大きい（例: > 5）、周期パターン除去後も D が大きい | セール、チケット販売、プッシュ通知、ボット | **total ＋ naive の組み合わせ条件** | 容量（キャパシティ）監視、イベント前の運用ルール |

### 6-3. 判定の手順

1. 窓（1時間、5分）ごとのリクエスト数 N を出す
2. 次の指標を計算する（§8 のスクリプト）
   - 最小 N と、`1 ÷ (T × (1 − SLO))` を下回る窓の割合 → 軸A
   - r の 1% 点 / 99% 点 → 軸B / 軸C
   - 分散指数 D（ポアソンなら 1）と、曜日・時刻の平均を引いた後の D → B と C のどちらが主か
3. §6-2 の表でタイプを決める
4. §7 のアラート構成から、そのタイプの行を採用する
5. 運用しながら「誤報だった」「見逃した」を記録し、基準を調整する

## 7. アラートの構成例（他のアラートとの併用）

| 目的 | 条件の例 | 対応 | 対象タイプ |
|---|---|---|---|
| **予算の保護（急）** | total ≥ 14.4（1時間）かつ total ≥ 14.4（5分） | すぐに人を呼ぶ | ③④ |
| **予算の保護（じわじわ）** | total ≥ 6（6時間）かつ total ≥ 6（30分） | 人を呼ぶ | ③④ |
| **予算の保護（ゆっくり）** | total ≥ 1（3日）かつ total ≥ 1（6時間） | チケット | ③④ |
| **異常の検知** | naive ≥ 14.4（1時間）かつ 失敗数 ≥ 数件（例: 5件） | 人を呼ぶ | ①（③で total と併用も可） |
| **スパイク時の誤報防止** | 上の total 条件に「**かつ naive ≥ 2倍程度**」を追加 | — | ④ |
| **全停止の検知** | 10分間、成功リクエストが 0件（かつ普段その時間帯に数件以上来る） / 合成リクエストが連続失敗 | すぐに人を呼ぶ | 全タイプ（特に ③） |
| **容量の監視** | リクエスト数が平均の数倍以上、CPU・キュー長など | 人を呼ぶ / 自動スケール | ④ |
| **予定されたイベント** | セール前後は変更を止める、残り予算を事前に確保する（エラーバジェットポリシー） | 運用ルール | ④ |

ポイント:
- 「失敗数 ≥ 数件」の条件は §3-1 の誤報（1件の失敗で鳴る）を防ぐ
- 「naive ≥ 2倍程度」の条件は §3-3（壊れていないのに鳴る）を防ぐ
- 全停止の検知は §3-2（total の見逃し）を補う
- **SLO のアラートは症状（ユーザー被害）を見るもの**。Hartmann も講演で、補完的なアラートの併用を勧めている

### 実装の例（Prometheus 風の擬似コード）

```
# naive（1時間窓）
(sum(increase(errors[1h])) / sum(increase(requests[1h]))) / 0.001

# total（1時間窓）: 分母は直近30日の1時間あたり平均
sum(increase(errors[1h])) / (sum(increase(requests[30d])) / 720) / 0.001
```

`requests[30d]` の計算が重い場合は、Hartmann の講演の通り、周期の総数を1日1回計算して定数として使う。

[`06-traffic-profile.py`](06-traffic-profile.py)（入力は `Time` と `total` 列を持つ TSV。`datasets/slo_requests.csv` と同じ形式）

```bash

```

スクリプト冒頭の `SLO` / `T` / `WINDOW` を自分のサービスに合わせて変える。
N̄ はファイル全体の平均（直近30日のデータを入れれば、直近30日の平均になる）。

### 例: `datasets/slo_requests.csv`（SLO 99.9% と仮定、1時間窓）

| 指標 | 値 | 読み方 |
|---|---|---|
| 窓あたり平均 N̄ | 343.0 | — |
| 窓あたり最小 N | 3.1 | 69 を大きく下回る → 軸A・Bの問題あり |
| N < 69 の窓の割合 | 6.1% | この時間帯は naive が1件の失敗で鳴る |
| 分散指数 D | 173.6 | ポアソン（1）から大きく外れる |
| 周期パターン除去後の D | 54.1 | 下がるがまだ大きい |
| 周期パターンで説明できる割合 | 69% | 主に周期的な波（軸B）、残りは予測できない変動（軸C） |
| r の 1% 点 / 99% 点 | 0.12 / 3.56 | 谷が深い。山はそれほど高くない |
| total が全停止を見逃す窓の割合 | 0.3% | r < 0.0144 になる窓はほとんどない |
| r ≥ 14.4 の窓の割合 | 0.0% | 急増だけで total が鳴ることはない |

→ **タイプ③（周期的な波が大きい）**。主に total、併用で全停止検知。
（データが2週間分しかないので、曜日・時刻ごとの平均は2点ずつ。正確に判定するにはもっと長いデータが必要）
