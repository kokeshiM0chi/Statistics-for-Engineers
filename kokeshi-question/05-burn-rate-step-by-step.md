## 参考: Google の基準値（14.4倍・6倍・1倍）の導出

### 出発点: Google SRE Workbook のルール

Google SRE Workbook（5章 "Alerting on SLOs"）は、**SLO 周期を30日**として、次のルールを推奨している。

| ルール（人が決めた方針） | 対応 |
|---|---|
| **1時間**で、30日分の予算の **2%** を使った | すぐに人を呼ぶ（page） |
| **6時間**で、30日分の予算の **5%** を使った | 人を呼ぶ（page） |
| **3日**で、30日分の予算の **10%** を使った | チケットを切る（営業時間内に対応） |

「何時間で予算の何%」はそのままだと監視ツールに設定しにくいので、**バーンレート（何倍のペースか）に変換**する。
その変換結果が 14.4倍・6倍・1倍。

### 準備: 1倍のペースとは

バーンレート 1倍 = 「30日（720時間）かけて、ちょうど予算を使い切る」速さ。

```
30日 = 30 × 24 = 720時間
```

1倍のペースで T 時間たつと、予算をどれだけ使うか:

```
1倍のペースで T 時間に使う予算 = T ÷ 720
```

| T | 1倍のペースで使う予算 |
|---|---|
| 1時間 | 1 ÷ 720 = 0.00139 = **0.139%** |
| 6時間 | 6 ÷ 720 = 0.00833 = **0.833%** |
| 3日 = 72時間 | 72 ÷ 720 = 0.1 = **10%** |

### バーンレートの定義

```
バーンレート = 実際に T 時間で使った予算 ÷ 1倍のペースで T 時間に使う予算
```

### 導出1: 1時間で2% → 14.4倍

```
実際に使った予算           = 2% = 0.02
1倍のペースで1時間に使う予算 = 1 ÷ 720 = 0.00139

バーンレート = 0.02 ÷ (1 ÷ 720)
            = 0.02 × 720
            = 14.4倍
```

### 導出2: 6時間で5% → 6倍

```
実際に使った予算           = 5% = 0.05
1倍のペースで6時間に使う予算 = 6 ÷ 720 = 0.00833

バーンレート = 0.05 ÷ (6 ÷ 720)
            = 0.05 × 720 ÷ 6
            = 36 ÷ 6
            = 6倍
```

### 導出3: 3日（72時間）で10% → 1倍

```
実際に使った予算            = 10% = 0.10
1倍のペースで72時間に使う予算 = 72 ÷ 720 = 0.10

バーンレート = 0.10 ÷ (72 ÷ 720)
            = 0.10 ÷ 0.10
            = 1倍
```

### 一般式

```
基準のバーンレート = 使ってよい予算の割合 × (周期の時間数 ÷ 判定する時間幅)
```

| ルール | 計算 | 基準 |
|---|---|---|
| 1時間で2% | 0.02 × (720 ÷ 1) | **14.4倍** |
| 6時間で5% | 0.05 × (720 ÷ 6) | **6倍** |
| 3日で10% | 0.10 × (720 ÷ 72) | **1倍** |

### 逆算: 14.4倍が1時間続くと、予算をどれだけ使うか

```
14.4倍 × (1 ÷ 720) = 14.4 ÷ 720 = 0.02 = 2%   ← 元のルールに戻る
```

### 周期が28日の場合（2023年ノートブックの設定）

```
28日 = 28 × 24 = 672時間
```

| ルール | 計算 | 基準 |
|---|---|---|
| 1時間で2% | 0.02 × (672 ÷ 1) | **13.44倍** |
| 6時間で5% | 0.05 × (672 ÷ 6) | **5.6倍** |
| 3日で10% | 0.10 × (672 ÷ 72) | **約0.93倍** |

ノートブックのセル10は、目安として 14倍の線を引いている。

### 短い窓（確認用）の組み合わせ

Workbook では、長い窓に加えて**長さ 1/12 の短い窓でも同じ基準を超えているとき**にだけアラートを出すことを推奨している。

| 長い窓 | 短い窓 | 基準 |
|---|---|---|
| 1時間 | 5分 | 14.4倍 |
| 6時間 | 30分 | 6倍 |
| 3日 | 6時間 | 1倍 |

- 長い窓: 一瞬のノイズで鳴らないようにする
- 短い窓: 障害が収まったらすぐにアラートが止まるようにする（長い窓だけだと、収まった後も1時間鳴り続ける）

### 大事な点

14.4 という数字は自然法則ではなく、「**1時間で予算の2%を使ったら夜中でも人を呼ぶ**」という**運用方針から逆算した値**。
チームやサービスに合わせて「2%」を変えれば、基準の倍率も変わる。

### 備考: 2% / 5% / 10% はどういう意味合いの値か

**位置づけ**: 理論から導いた値ではなく、Workbook が「reasonable starting numbers（妥当な出発点）」として勧める**経験的な値**。
ただし適当な数字ではなく、次のような意味合いで選ばれている。

**(1) 「このペースが続いたら、予算はいつ尽きるか」で急ぎ度を3段階に分けている**

```
予算が尽きるまで = 周期 ÷ バーンレート
```

| ルール | 予算が尽きるまで | 意味合い | 対応 |
|---|---|---|---|
| 1時間で2%（14.4倍） | 30日 ÷ 14.4 = **約2日** | 放っておくと週末のうちに予算がなくなる | 夜中でも起きる |
| 6時間で5%（6倍） | 30日 ÷ 6 = **5日** | 放っておくと平日のうちになくなる | 今日中に対応 |
| 3日で10%（1倍） | 30日 ÷ 1 = **30日** | 周期の終わりにちょうど使い切るペース。急がないが放置もできない | 営業時間内にチケットで対応 |

**(2) 深刻な障害ほど速く鳴るようになっている**

```
検知までの時間 = 窓の長さ × 基準の倍率 ÷ 実際のバーンレート
```

| 障害の大きさ（SLO 99.9%） | 実際のバーンレート | 1時間・14.4倍ルールで鳴るまで |
|---|---|---|
| 全停止（エラー率100%） | 100% ÷ 0.1% = 1,000倍 | 1時間 × 14.4 ÷ 1,000 ≈ **52秒** |
| エラー率10% | 10% ÷ 0.1% = 100倍 | 1時間 × 14.4 ÷ 100 ≈ **約9分** |
| エラー率1.44%（ちょうど基準） | 14.4倍 | 1時間 × 14.4 ÷ 14.4 = **1時間** |

全停止なら約1分で鳴り、基準ぎりぎりの軽い障害は1時間様子を見てから鳴る。

**(3) 「チーム健全性」と「見逃さないこと」の折り合いをつける値**

Workbook はアラートの良し悪しを4つの観点で評価している。

| 観点 | 意味 |
|---|---|
| 精度（precision） | 鳴ったアラートが本当に重要か（誤報が少ないか） |
| 再現率（recall） | 重要な障害を見逃さないか |
| 検知時間 | 障害が始まってから鳴るまでの速さ |
| 復帰時間 | 障害が収まってからアラートが止まるまでの速さ |

- 2% を**小さく**する → 見逃しが減り検知も速いが、誤報が増えて夜中に何度も起こされる
- 2% を**大きく**する → 誤報は減るが、見逃しや検知の遅れが増える

→ #01 の質問にあった「チーム健全性とアラート」のトレードオフを、どこで折り合いをつけるかを数字にしたもの。

**(4) 実務では調整する前提**

1. まず Google の値（2% / 5% / 10%）で始める
2. 「鳴ったけど対応不要だった」「鳴らなかったけど障害だった」を記録する
3. その記録をもとにチームで調整する（周期が28日なら 13.4倍 / 5.6倍 / 約0.93倍 にする、など）

## 0. 準備: 例で使う数字

| 項目 | 値 |
|---|---|
| SLO | 99.9%（= 0.999） |
| 周期 | 30日 = 30 × 24 = **720時間** |
| 平均トラフィック | 1時間に **10,000リクエスト** |

ここから次の4つを計算しておく。

**(1) 許容エラー率**
```
1 − SLO = 1 − 0.999 = 0.001 = 0.1%
```

**(2) 30日間の総リクエスト数**
```
10,000件/時間 × 720時間 = 7,200,000件
```

**(3) エラーバジェット（30日間で失敗してよい件数）**
```
許容エラー率 × 総リクエスト数 = 0.001 × 7,200,000 = 7,200件
```

**(4) 1倍のペース（1時間に何件の失敗なら、ちょうど30日で使い切るか）**
```
7,200件 ÷ 720時間 = 10件/時間
```

## バーンレートの計算手順（毎回この4ステップ）

```
ステップ1  エラー率     = その時間幅の失敗数の合計 ÷ その時間幅のリクエスト数の合計
ステップ2  バーンレート = エラー率 ÷ 許容エラー率(0.001)
ステップ3  判定         = バーンレートを基準（14.4倍 / 6倍 / 1倍）と比べる
ステップ4  実感         = 予算がなくなるまでの日数 = 30日 ÷ バーンレート
```

注意: エラー率は「合計してから割る」。1分ごとのエラー率を平均してはいけない（件数の少ない1分が同じ重みの1票になってしまう）。

## ケースA: 1時間に 10,000リクエスト中、5件失敗

**ステップ1: エラー率**
```
5 ÷ 10,000 = 0.0005 = 0.05%
```

**ステップ2: バーンレート**
```
0.0005 ÷ 0.001 = 0.5倍
```

**ステップ3: 判定**
- 1時間の基準 14.4倍 → 0.5 < 14.4 で届かない
- 3日の基準 1倍 → 0.5 < 1 で届かない
- → **何もしない**

**ステップ4: 実感**
```
30日 ÷ 0.5 = 60日   → 30日の周期内では予算は尽きない
この1時間で使った予算 = 5件 ÷ 7,200件 = 0.07%
```

## ケースB: 1時間に 10,000リクエスト中、30件失敗（何日も続く）

**ステップ1: エラー率**
```
30 ÷ 10,000 = 0.003 = 0.3%
```

**ステップ2: バーンレート**
```
0.003 ÷ 0.001 = 3倍
```

**ステップ3: 判定**
- 1時間の基準 14.4倍 → 3 < 14.4 で届かない
- 6時間の基準 6倍 → 3 < 6 で届かない
- 3日の基準 1倍 → 3 > 1 で**超える**
- → **チケットを切って営業時間内に対応**

**ステップ4: 実感**
```
30日 ÷ 3 = 10日   → このまま続くと10日で予算が尽きる
この1時間で使った予算 = 30件 ÷ 7,200件 = 0.42%
```

## ケースC: 1時間に 10,000リクエスト中、80件失敗（6時間続く）

**ステップ1: エラー率**
```
80 ÷ 10,000 = 0.008 = 0.8%
```

**ステップ2: バーンレート**
```
0.008 ÷ 0.001 = 8倍
```

**ステップ3: 判定**
- 1時間の基準 14.4倍 → 8 < 14.4 で届かない
- 6時間の基準 6倍 → 6時間の合計で計算し直す
  ```
  6時間の失敗数       = 80 × 6 = 480件
  6時間のリクエスト数 = 10,000 × 6 = 60,000件
  エラー率           = 480 ÷ 60,000 = 0.008
  バーンレート        = 0.008 ÷ 0.001 = 8倍  → 8 > 6 で超える
  ```
- → **人を呼ぶ**

**ステップ4: 実感**
```
30日 ÷ 8 = 3.75日   → このまま続くと4日弱で予算が尽きる
6時間で使った予算 = 480件 ÷ 7,200件 = 6.7%
```

```
500 ÷ 10,000 = 0.05 = 5%
```

**ステップ2: バーンレート**

```
0.05 ÷ 0.001 = 50倍
```

**ステップ3: 判定**


## ケースE: 夜中、1時間に100リクエストしか来ず、2件失敗

### naive 方式（Google 標準: 分母はその1時間の実際のリクエスト数）

**ステップ1: エラー率**
```
2 ÷ 100 = 0.02 = 2%
```

**ステップ2: バーンレート**
```
0.02 ÷ 0.001 = 20倍
```

**ステップ3: 判定**
- 20 > 14.4 で、**人を呼ぶことになってしまう**

### total 方式（Hartmann 方式: 分母は周期の平均リクエスト数）

**ステップ1: エラー率**（分母を1時間あたりの平均 10,000件にする）
```
2 ÷ 10,000 = 0.0002 = 0.02%
```

**ステップ2: バーンレート**
```
0.0002 ÷ 0.001 = 0.2倍
```

**ステップ3: 判定**
- 0.2 < 14.4 で、**呼ばない**

**ステップ4: 実感**（使った予算はどちらの方式でも同じ）
```
この1時間で使った予算 = 2件 ÷ 7,200件 = 0.03%
```

実際に使った予算はたった 0.03%。total 方式の判定（呼ばない）のほうが実態に合っている。

## 検算: 「失敗件数 ÷ 1倍のペース（10件/時間）」でも同じ答え

その1時間のリクエスト数が平均と同じ（10,000件）なら、失敗件数を 1倍のペースで割るだけでもバーンレートが出る。

| ケース | 1時間の失敗数 ÷ 10件 | 上の計算結果 |
|---|---|---|
| A | 5 ÷ 10 = 0.5倍 | 0.5倍 ✓ |
| B | 30 ÷ 10 = 3倍 | 3倍 ✓ |
| C | 80 ÷ 10 = 8倍 | 8倍 ✓ |
| D | 500 ÷ 10 = 50倍 | 50倍 ✓ |
| E（total） | 2 ÷ 10 = 0.2倍 | 0.2倍 ✓ |

total 方式は、まさに「**その1時間の失敗件数が、1倍のペースの何倍か**」を数えていることになる。

## Google 標準（naive）の課題と、Hartmann の改良（total バーンレート）

### 1. Google 標準: naive バーンレート

ここまでの計算手順そのもの。Google SRE Workbook の多窓・多バーンレートのアラートはこの形。

```
naive バーンレート = (窓内の失敗数 ÷ 窓内のリクエスト数) ÷ (1 − SLO)
                     └──── その窓で実際に来た件数で割る ────┘
```

トラフィックが一定なら問題なく働く。

### 2. 課題: リクエスト数が少ない時間に、1件の失敗が大障害に見える

ケースEの通り、夜中の 100件中2件の失敗が **20倍** になり、14.4倍を超えて人が呼ばれる。
実際に使った予算は 0.03% にすぎない。

Google 自身も Workbook の「Low-Traffic Services and Error Budget Alerting」の節でこの問題を認めていて、
次の**運用上の回避策**を挙げている（計算式は変えない）。

| 回避策 | 内容 | 弱点 |
|---|---|---|
| 合成トラフィック | 監視用のリクエストを流して件数を増やす | 本物のリクエストの種類を網羅しにくい。成功した合成リクエストが本物の失敗を薄めることがある |
| サービスを束ねる | 同じ機能を担う小さなサービスをまとめて1つの SLO にする | 1つのサービスだけ全停止しても気づきにくい |
| サービス側を変える | クライアントのリトライ（指数バックオフ + ジッター）や、後で再実行できる仕組みで、1件の失敗の影響を減らす | 実装の手間がかかる |
| SLO を下げる / 窓を長くする | 1件の失敗で基準を超えないようにする | プロダクト側との合意が必要。気づくのが遅れる |

### 3. Hartmann の改良: 分母を「周期の平均リクエスト数」にする

2023年の講演「Mathematics of SLOs」とノートブック（セル9〜10）では、naive と並べて **total バーンレート**を示している。
運用で回避するのではなく、**計算式の分母を変える**アプローチ。

```
total バーンレート = (窓内の失敗数 ÷ 周期の平均で見た窓内のリクエスト数) ÷ (1 − SLO)
                     └──── 平均的なトラフィックなら来ていたはずの件数で割る ────┘
```

ノートブックのコード（セル10、1時間窓）:

```python
M = pd.Timedelta(period) / pd.Timedelta("1h")        # 周期の時間数（28日 → 672）
I = lambda s: s.rolling(period).sum()                # 周期（28日）の合計
df['burn_rate_naive'] = df['error_rate'] / (1-slo)
df['burn_rate_total'] = df['bad'].rolling("1h").sum() * M / I(df['total']) / (1-slo)
#                       └ 直近1時間の失敗数  └ I(total)/M = 1時間あたりの平均リクエスト数
```

### 4. なぜこれが自然なのか: 予算は「件数」で決まっているから

エラーバジェットは「周期内で失敗してよい**件数**」（0. 準備の (3)、この例では 7,200件）。
total バーンレートを変形すると、

```
total バーンレート = 窓内の失敗数 ÷ (1倍のペースで窓内に失敗してよい件数)
                  = 窓内の失敗数 ÷ (7,200件 × 窓の長さ ÷ 720時間)
```

つまり「**予算を件数で減らしているスピード**」をそのまま測っている（「検算」の節の計算と同じ）。
予算を件数で数えるなら、減るスピードも件数で測るのが筋、という考え方。

### 5. トラフィックが一定なら、naive と total は同じ値になる

窓内のリクエスト数がちょうど平均と同じ（例: 1時間に10,000件）なら、2つの式の分母が一致する。
ケースA〜Dが naive でも total でも同じ答えになるのはこのため。
→ **基準（14.4倍 など）はそのまま使える**。違いが出るのはトラフィックが平均から外れたときだけ。

Hartmann は 28日周期で「1時間で予算の2%」を基準にしていて、0.02 × 672 = **約13.4倍**（ノートブックの線は目安の14倍）。

### 6. total の弱点（Hartmann 自身も講演で指摘）

total は naive が拾えるケースを見逃すことがある。逆に naive が見逃すケースを拾うこともある。

**夜中の全停止を見逃す**（1時間に100リクエスト、全部失敗）

```
naive: (100 ÷ 100)    ÷ 0.001 = 1 ÷ 0.001      = 1,000倍  → 呼ぶ
total: (100 ÷ 10,000) ÷ 0.001 = 0.01 ÷ 0.001   = 10倍     → 呼ばない（14.4倍未満）
```

使った予算は 100 ÷ 7,200 = 1.4% で、「予算の観点」では呼ばないのが正しい。
しかし**サービスが完全に止まっている**ので、朝まで放置するのは困る。

**日中のピークで、中程度のエラーを拾う**（セール中、1時間に30,000リクエスト、150件失敗）

```
naive: (150 ÷ 30,000) ÷ 0.001 = 0.005 ÷ 0.001  = 5倍   → 呼ばない
total: (150 ÷ 10,000) ÷ 0.001 = 0.015 ÷ 0.001  = 15倍  → 呼ぶ
```

使った予算は 150 ÷ 7,200 = 2.1% で、1時間で2%を超えている。**total の判定が正しい**。
naive はエラー率が小さく見えるので、ピーク時の大量の被害を見逃す。

| 状況 | naive | total | 予算の観点で正しいのは |
|---|---|---|---|
| 夜中、100件中2件失敗 | 20倍 → 呼ぶ | 0.2倍 → 呼ばない | total |
| 夜中、100件全部失敗 | 1,000倍 → 呼ぶ | 10倍 → 呼ばない | total（ただし全停止は別途検知したい） |
| ピーク、30,000件中150件失敗 | 5倍 → 呼ばない | 15倍 → 呼ぶ | total |

そのため Hartmann は、**SLO のアラートだけに頼らず、補完的なアラートを併用する**ことを勧めている。
例: 「10分間、成功リクエストが0件」のような全停止検知、合成リクエストによる死活監視。

### 7. おまけ: 残り予算による運用方針（講演より）

| 残り予算 | 方針 |
|---|---|
| 20%より多い | 通常通り開発・リリース |
| 20%以下 | リリースは慎重に。ポストモーテムの改善項目を優先 |
| 0%以下（SLO 違反） | 新機能の開発を止めて、信頼性の改善に投資 |

### 補足: 誰が最初に考えたか

total 型の考え方（件数ベースでバーンレートを測る）を Hartmann が最初に提案したかどうかは確認できていない。
ここで書いているのは、**Google Workbook が運用の工夫で回避している問題を、Hartmann は講演で計算式の側から解決する方法として示している**、ということ。
