# kokeshi-question #01: リクエスト数に差がある時間帯の SLO / エラーバジェット

## 質問

> リクエスト数が高い時と低い時で、エラーバジェットを同じにしてしまうと、例えば真夜中の５回のリクエストで１回の失敗が20％と評価されてしまう。これは実際のユーザ体験の悪化を表現しているとは言い難く、これによってチームにアラートを出すとチーム健全性も保てない。
> 夜中と日中などリクエスト数に差がある場合のエラーバジェットや SLO はどう考えるべきか。リクエスト数に差がある場合、分位数の考え方は相性が良くないと述べているようだがどうしたらいいのか。

## 1. 夜間の少ないリクエストをどう評価するか — Total Burn Rate

一番の答えは [`2023-10-11-SRECon-Dublin/2023-10-08 SLOs at SRECon.ipynb`](../2023-10-11-SRECon-Dublin/2023-10-08%20SLOs%20at%20SRECon.ipynb) の **Burn Rate** 章。2種類のバーンレートを比較している。

```python
df['burn_rate_naive'] = df['error_rate'] / (1-slo)                 # その瞬間のエラー率
df['burn_rate_total'] = df['bad'] / A(df['total']) / (1-slo)       # 直近28日の平均リクエスト数で割る
```

| | 計算 | 夜中 5件中1件失敗、SLO 98% の場合 |
|---|---|---|
| **naive** | その分のエラー率 `bad/total` を使う | 0.2 / 0.02 = **10倍** → アラートが鳴る |
| **total** | 失敗数を**直近28日の平均リクエスト数**で割る | 平均 100件/分なら 0.01 / 0.02 = **0.5倍** → 予算消費として正しく小さい |

### 核心: エラーバジェットを「率」ではなく「失敗件数の予算」として扱う

- バジェット = `(1 − SLO) × 期間内の総リクエスト数`
- 夜中の1件の失敗も、日中の1件の失敗も、同じ「1件分」だけ予算を消費する

→ 影響を受けたユーザー数に比例するので、「ユーザー体験の悪化」をより素直に表す。

ノートブックのグラフでは、naive は夜間にスパイクを連発する一方、total は本当に予算を燃やしている障害（データに注入された 08-14 深夜と 08-17 日中の障害）だけが目立つ。

## 2. 分位数（パーセンタイル）との相性問題と代替

分位数の問題は2つのノートブックで扱われている。

1. **少数サンプルの分位数は統計的に不安定**
   — [`2022-10-24-SRECon-Amsterdam`](../2022-10-24-SRECon-Amsterdam/SRECon%20EMEA%202022%20Amsterdam.ipynb) の Sampling 章
   - 相対誤差 ≈ `√((1−p)/(pN))` で、N が小さいと急増する。夜中の5件の p99 はほぼ無意味。
2. **時間帯ごとの分位数は平均できない**
   — [`2019-10-02-SRECon-Dublin/2.2 Aggregating Percentiles.ipynb`](../2019-10-02-SRECon-Dublin/2.2%20Aggregating%20Percentiles.ipynb)
   - 1時間ごとの p90 の平均は 50% 超の誤差がよく出る。リクエスト数で重み付けしても直らない。

### 解決策: 「閾値以下の件数（count-below）」で SLI を定義する

- 「p99 < 300ms」ではなく、「300ms 未満で返ったリクエスト = good、それ以外 = bad」と数える
- 件数は単純に足し算できる（mergeable）ので、時間帯・ノードをまたいでも正確
- レイテンシ SLO も可用性と同じ good/bad 比率になる → **上の total burn rate がそのまま使える**
- 閾値を後から変えたい / 分布全体を見たい場合は、マージ可能なヒストグラムを保存する
  - circllhist / HDR Histogram / t-digest / DDSketch
  - 比較: [`2019-10-02-SRECon-Dublin/2.3 Histograms.ipynb`](../2019-10-02-SRECon-Dublin/2.3%20Histograms.ipynb), [`2.4 Mergeable Percentile Aggregation Comparison.ipynb`](../2019-10-02-SRECon-Dublin/2.4%20Mergeable%20Percentile%20Aggregation%20Comparison.ipynb)

## 3. チーム健全性とアラート設計（リポジトリ外の一般的プラクティス）

リポジトリが直接扱うのは 1・2 まで。実務では Google SRE Workbook などの定番と組み合わせる。

- **アラートはエラー率ではなくバーンレートに対して出す** — 深夜の単発失敗では起こされない
- **マルチウィンドウ × マルチバーンレート**
  - 例: 「1時間で 14.4倍 かつ 5分で 14.4倍」→ 即ページ
  - 「6時間で 6倍」→ ページ
  - 「3日で 1倍」程度 → チケット（夜間は起こさない）
- **最小イベント数条件** — ウィンドウ内のリクエストが N 件未満なら判定しない
- **本当にトラフィックが少ないサービス** — 合成リクエスト（synthetic probe）で母数を補う、または関連サービスを束ねて1つの SLO にする
- **リリースと安定性のトレードオフ** — Error Budget Policy で「予算があるうちはリリース優先、尽きたら安定化優先」を事前に合意しておき、都度の対立を減らす

## まとめ

**「エラー率」ではなく「失敗件数」で予算を数え、「分位数」ではなく「閾値で good/bad を数える」**。
これで時間帯によるリクエスト数差の問題はほぼ解消できる。
